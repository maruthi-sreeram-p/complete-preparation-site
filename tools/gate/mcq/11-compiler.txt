?2 [Bottom-up parsing] The grammar S → L = R | R, L → * R | i, R → L is
(a) LR(0)
(b) SLR(1) but not LR(0)
(c)* LALR(1) but not SLR(1)
(d) not LR(1)
=> After L, the state contains S → L • = R and R → L •. FOLLOW(R) contains =, so SLR(1) sees a shift/reduce conflict on =. The true lookahead for that reduction is only $, so LALR(1) and CLR(1) have no conflict.
!py

?2 [Bottom-up parsing] The grammar S → a A d | b B d | a B e | b A e, A → c, B → c is
(a) SLR(1)
(b) LALR(1) but not SLR(1)
(c)* CLR(1) (canonical LR(1)) but not LALR(1)
(d) not LR(1)
=> After a c the lookahead d means reduce c to A and e means reduce c to B (and the reverse after b c). Canonical LR(1) keeps the two states apart. LALR(1) merges them, because they have the same core, and the merged state has a reduce/reduce conflict.
!py
k = lr_kind({'S': ['aAd', 'bBd', 'aBe', 'bAe'], 'A': ['c'], 'B': ['c']}, 'S')
assert k['clr'] and not k['lalr'] and not k['slr']

?2 [Bottom-up parsing] The grammar E → E + T | T, T → T * F | F, F → ( E ) | i is
(a) LR(0)
(b)* SLR(1) but not LR(0)
(c) LALR(1) but not SLR(1)
(d) CLR(1) but not LALR(1)
=> The state containing E → T • and T → T • * F has a shift (on *) and a complete item. That is a conflict in LR(0). In SLR(1) the reduction applies only on FOLLOW(E) = { + , ) , $ }, which does not contain *, so SLR(1) resolves it.
!py

?2 [Bottom-up parsing] Which of the following statements about LR parsers is FALSE?

(b) A CLR(1) parser can have more states than an LALR(1) parser for the same grammar

=> Multiplication binds tighter: 4 * 2 = 8, then 3 + 8 = 11. The compiler computes this at compile time.

?1 [Optimisation and data-flow analysis] The standard data-flow equation for reaching definitions is
(a)* OUT[B] = gen[B] ∪ (IN[B] − kill[B])
(b) IN[B] = use[B] ∪ (OUT[B] − def[B])

?2 [Optimisation and data-flow analysis] Block B1 computes a + b. Block B2 contains the assignment a = 1. Block B3 follows. The edges are B1 → B3 and B1 → B2 → B3. Is the expression a + b available at the entry of B3?
(a) Yes, because B1 computes it
(b)* No, because it is killed along the path through B2
(c) Yes, because it is computed on at least one path
(d) It cannot be determined
=> Availability requires the expression to be computed and not killed on every path. On the path through B2, a is redefined, so a + b is not available there. The intersection over both predecessors is empty.
