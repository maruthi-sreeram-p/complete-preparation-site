?1 [SOLID] The single responsibility principle states that
(a) a class should have only one method
(b)* a class should have only one reason to change
(c) a class should be open for extension but closed for modification
(d) a class should depend on abstractions
=> SRP is about cohesion around one responsibility: if a class changes for several unrelated reasons (business rules, formatting, persistence), it should be split. Option (c) is the open/closed principle and (d) the dependency inversion principle.

?2 [SOLID] A `Bird` class has a method `fly()`. A `Penguin` class extends `Bird` and overrides `fly()` to throw `UnsupportedOperationException`. Code that works with any `Bird` now crashes for penguins. The principle violated is
(a) single responsibility
(b) open/closed
(c)* Liskov substitution
(d) interface segregation
=> A Penguin cannot be substituted for a Bird without breaking code that relies on `fly()`. The hierarchy promises more than the subtype can deliver. A better design separates `Bird` from a `FlyingBird` capability.

?2 [SOLID] A `Worker` interface declares `work()`, `eat()` and `sleep()`. A `Robot` class implements it and has to write empty or exception-throwing `eat()` and `sleep()` methods. The principle violated is
(a) Liskov substitution
(b) single responsibility
(c)* interface segregation
(d) dependency inversion
=> The interface is too fat: Robot is forced to depend on methods it does not use. Split it into small role interfaces such as `Workable` and `Feedable`, and implement only the ones that apply.

?2 [SOLID] A method calculates the area of shapes with an if/else chain on a type code (CIRCLE, SQUARE, ...). Every new shape means editing this method. The best fix, and the principle behind it, is
(a)* give each shape its own class implementing an area() method (open/closed principle)
(b) move the method to a utility class (single responsibility)
(c) make the type code a constant (don't repeat yourself)
(d) use a static method (dependency inversion)
=> Replacing the conditional with polymorphism lets you add a shape by adding a class, without modifying existing, tested code: open for extension, closed for modification.

?1 [SOLID] The dependency inversion principle says that
(a) subclasses must be substitutable for their parents
(b)* high-level modules should depend on abstractions, not on concrete low-level modules
(c) interfaces should be small
(d) classes should be immutable
=> Business logic should depend on an interface and receive its implementation from outside (dependency injection), so low-level details such as the database or the mail library can be swapped or faked in tests.

?1 [Principles] The Law of Demeter is most clearly violated by the call
(a) `order.total()`
(b)* `order.getCustomer().getAddress().getCity()`
(c) `Math.max(a, b)`
(d) `list.size()`
=> Reaching through several objects couples the caller to the structure of Order, Customer and Address. The principle says to talk only to your immediate collaborators, for example `order.shippingCity()`.

?1 [Principles] A well-designed class has
(a) low cohesion and high coupling
(b) high cohesion and high coupling
(c)* high cohesion and low coupling
(d) low cohesion and low coupling
=> High cohesion means the members of the class belong together; low coupling means it depends on few other classes and only through narrow interfaces. Together they make a class easy to understand and change.

?2 [Decorator] What does this program print?
```java
public class Main {
    interface Coffee { double cost(); }
    static class Plain implements Coffee { public double cost() { return 2.0; } }
    static class Milk implements Coffee {
        private final Coffee inner;
        Milk(Coffee inner) { this.inner = inner; }
        public double cost() { return inner.cost() + 0.5; }
    }
    static class Sugar implements Coffee {
        private final Coffee inner;
        Sugar(Coffee inner) { this.inner = inner; }
        public double cost() { return inner.cost() + 0.25; }
    }
    public static void main(String[] args) {
        Coffee c = new Sugar(new Milk(new Milk(new Plain())));
        System.out.println(c.cost());
    }
}
```
(a) 2.25
(b) 2.5
(c)* 3.25
(d) 2.75
=> Each decorator wraps another Coffee and adds its price: Plain 2.0, plus two Milk (0.5 each) gives 3.0, plus Sugar 0.25 gives 3.25.

?2 [Strategy] What does this program print?
```java
import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<String> words = new ArrayList<>(List.of("pear", "fig", "banana", "kiwi"));
        words.sort(Comparator.comparingInt(String::length).thenComparing(Comparator.reverseOrder()));
        System.out.println(words);
    }
}
```
(a) [fig, kiwi, pear, banana]
(b)* [fig, pear, kiwi, banana]
(c) [banana, pear, kiwi, fig]
(d) [fig, kiwi, pear, banana, ]
=> The strategy (comparator) sorts by length first: fig (3), then the 4-letter words, then banana (6). Among equal lengths the second comparator sorts in reverse alphabetical order, so pear comes before kiwi.

?2 [Observer] What does this program print?
```java
import java.util.*;
import java.util.function.Consumer;

public class Main {
    static class Subject {
        private final List<Consumer<Integer>> observers = new ArrayList<>();
        void subscribe(Consumer<Integer> o) { observers.add(o); }
        void publish(int v) { observers.forEach(o -> o.accept(v)); }
    }
    public static void main(String[] args) {
        Subject s = new Subject();
        int[] total = {0};
        s.subscribe(v -> total[0] += v);
        s.subscribe(v -> total[0] += v * 10);
        s.publish(1);
        s.publish(2);
        System.out.println(total[0]);
    }
}
```
(a) 3
(b) 30
(c)* 33
(d) 36
=> Each of the two publications notifies both observers: the first adds v and the second adds 10v. Published values 1 and 2 give (1 + 10) + (2 + 20) = 33.
!py assert printed(stem) == ans.split()

?1 [Patterns] `new BufferedReader(new InputStreamReader(System.in))` is an example of the
(a) Singleton pattern
(b) Factory method pattern
(c)* Decorator pattern
(d) Observer pattern
=> Each reader wraps another reader and adds behaviour (character decoding, then buffering) while keeping a compatible interface, which is the Decorator pattern.

?1 [Patterns] The recommended way to implement a thread-safe, serialisation-safe singleton in Java is
(a) a public static field initialised in a static block
(b) a private constructor with a synchronised getInstance method
(c)* a single-element enum
(d) a class with only static methods and no constructor
=> An enum with one constant is guaranteed by the JVM to have exactly one instance, even against serialisation and reflection attacks, with no explicit locking.

?2 [UML] In a UML class diagram, a `House` has several `Room` objects, and the rooms cannot exist when the house is destroyed. The relationship is
(a) association
(b) aggregation
(c)* composition
(d) dependency
=> Composition is a strong whole-part relationship in which the part's lifetime is tied to the whole. Aggregation would suit a weaker relationship where the parts can outlive the whole, such as players and a team.

?2 [UML] A `Team` holds a list of `Player` objects, and the players continue to exist and may join another team if the team is disbanded. The relationship is best called
(a) composition
(b)* aggregation
(c) generalisation
(d) realisation
=> Aggregation is a has-a relationship in which the part has an independent life. Generalisation is inheritance and realisation is implementing an interface.

?2 [Factory] What does this program print?
```java
import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> list = List.of(1, 2, 3);
        try {
            list.add(4);
            System.out.println("added");
        } catch (UnsupportedOperationException e) {
            System.out.println("immutable");
        }
    }
}
```
(a) added
(b)* immutable
(c) a compile-time error
(d) [1, 2, 3, 4]
=> `List.of` is a static factory method that returns an unmodifiable list, so `add` throws UnsupportedOperationException. Static factories can return instances of any suitable type, here a compact immutable list.
