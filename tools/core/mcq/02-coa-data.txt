# Computer Organisation Part 2, data representation and arithmetic: original questions. Format: see tools/build_gate.py

?2 [Number systems] The hexadecimal value of the binary number 1101 0110 1011 is
(a) D5B
(b)* D6B
(c) B6D
(d) 6D6
=> Group the bits in fours: 1101 = D, 0110 = 6, 1011 = B, so the value is D6B.
!py assert int(ans, 16) == 0b110101101011

?2 [Signed integers] The 8-bit two's complement representation of −37 is
(a) 10100101
(b)* 11011011
(c) 11011010
(d) 01011011
=> +37 = 00100101. Inverting every bit gives 11011010 and adding 1 gives 11011011. The option 10100101 is the sign-magnitude form and 11011010 is the one's complement form.
!py assert ans == twos(-37, 8)

?1 [Signed integers] The range of integers that can be stored in n-bit two's complement is
(a) −2ⁿ to 2ⁿ − 1
(b)* −2ⁿ⁻¹ to 2ⁿ⁻¹ − 1
(c) −(2ⁿ⁻¹ − 1) to 2ⁿ⁻¹ − 1
(d) 0 to 2ⁿ − 1
=> With one sign bit of weight −2ⁿ⁻¹ the range is −2ⁿ⁻¹ to 2ⁿ⁻¹ − 1. There is one more negative number than positive numbers, and only one zero. Option (c) is the range of sign-magnitude and one's complement.

?2 [Overflow] Two 8-bit two's complement numbers 01101001 and 01011010 are added. The 8-bit result and the overflow status are
(a) 11000011, no overflow
(b)* 11000011, overflow
(c) 00111101, no overflow
(d) 00111101, overflow
=> 105 + 90 = 195, which does not fit in 8 bits (maximum 127). The bit pattern is 11000011, which reads as −61: two positive numbers gave a negative result, so signed overflow occurred.
!py assert add_overflows(105, 90, 8) and ans.startswith(twos(195 - 256, 8))

?2 [Overflow] Which of the following 8-bit two's complement additions causes overflow?
(a) 64 + 63
(b)* 64 + 64
(c) (−64) + (−64)
(d) 100 + (−100)
=> 64 + 64 = 128 exceeds the maximum 127. 64 + 63 = 127 fits, (−64) + (−64) = −128 fits exactly, and numbers of opposite signs can never overflow.
!py a, b = [int(t.strip("()")) for t in ans.replace("−", "-").split("+")]
!py assert add_overflows(a, b, 8)
!py assert not add_overflows(64, 63, 8) and not add_overflows(-64, -64, 8)

?2 [Signed integers] The 8-bit two's complement number 0xF5 is sign-extended to 16 bits. The result is
(a) 0x00F5
(b)* 0xFFF5
(c) 0xF5F5
(d) 0x80F5
=> 0xF5 = 11110101 has its sign bit set, so it is negative (−11). Sign extension copies the sign bit into the upper byte, giving 0xFFF5, which is still −11. 0x00F5 would be +245.
!py assert from_twos(format(0xF5, "08b")) == from_twos(format(int(ans, 16), "016b")) == -11

?2 [Floating point] The IEEE 754 single-precision representation of 5.5 in hexadecimal is
(a) 0x40A00000
(b)* 0x40B00000
(c) 0x41B00000
(d) 0x3FB00000
=> 5.5 = 101.1₂ = 1.011 × 2². The exponent is 2 + 127 = 129 = 10000001 and the fraction is 011 followed by zeros, so the bits are 0 10000001 01100000000000000000000 = 0x40B00000.
!py assert ieee32(5.5)[3] == ans[2:]

?2 [Floating point] The 32-bit pattern 0xC0A00000 is read as an IEEE 754 single-precision number. Its value is
(a) −2.5
(b)* −5
(c) −10
(d) −1.25
=> The sign bit is 1 (negative). The exponent field is 10000001 = 129, so the exponent is 129 − 127 = 2. The fraction 01000... gives a mantissa of 1.01₂ = 1.25. The value is −1.25 × 2² = −5.
!py assert ieee32_value("C0A00000") == -5.0 and num(ans) == -5

?1 [Floating point] The exponent bias of an IEEE 754 double-precision number is
(a) 127
(b)* 1023
(c) 1024
(d) 255
=> The double format has an 11-bit exponent, so the bias is 2¹⁰ − 1 = 1023. The bias 127 belongs to single precision (8-bit exponent).
!py assert num(ans) == 2 ** 10 - 1

?1 [Floating point] In IEEE 754, a number whose exponent field is all ones and whose fraction field is non-zero represents
(a) infinity
(b) a denormalised number
(c) zero
(d)* NaN (not a number)
=> All-ones exponent with zero fraction is ±infinity; with a non-zero fraction it is NaN. A denormal number has an all-zeros exponent field and a non-zero fraction.

?2 [Floating point] In Java, the expression 0.1 + 0.2 == 0.3 evaluates to
(a)* false, because 0.1 and 0.2 are not exactly representable and the sum is rounded
(b) true, because the arithmetic is exact for short decimals
(c) a compile-time error for comparing doubles
(d) true or false depending on the JVM version
=> 0.1 and 0.2 are stored as the nearest binary doubles; their sum is 0.30000000000000004, which differs from the double nearest to 0.3. The result is the same on every JVM because Java specifies IEEE 754 behaviour.
!py assert not (0.1 + 0.2 == 0.3)

?2 [Multiplication] Booth's algorithm scans the 7-bit multiplier 0111100. The number of add or subtract operations it performs is
(a) 1
(b)* 2
(c) 4
(d) 7
=> The run of four 1s begins at bit 5 and ends at bit 2, so Booth subtracts once at the start of the run and adds once after its end: 2 operations instead of the 4 additions plain shift-and-add would perform.
!py assert booth_ops("0111100", 7) == num(ans)

?2 [Error correction] The minimum number of check bits needed for a single-error-correcting Hamming code protecting 11 data bits is
(a) 3
(b)* 4
(c) 5
(d) 11
=> We need 2ʳ ≥ m + r + 1 = 11 + r + 1. For r = 3: 8 ≥ 15 is false. For r = 4: 16 ≥ 16 is true. So 4 check bits are needed, giving a 15-bit codeword.
!py assert hamming_parity_bits(11) == num(ans)

?2 [Overflow in code] A Java program computes `int x = Integer.MAX_VALUE; x = x + 1;`. The value of x afterwards is
(a) 2147483648
(b)* −2147483648
(c) 0
(d) an ArithmeticException is thrown
=> Java int arithmetic wraps around in two's complement and does not throw. 0x7FFFFFFF + 1 = 0x80000000, the most negative int. Use `Math.addExact` to get an exception instead.
!py assert from_twos(format((2 ** 31 - 1 + 1) & (2 ** 32 - 1), "032b")) == -2 ** 31 and num(ans) == -2 ** 31

?2 [Codes] The 4-bit Gray code of the decimal number 10 is
(a) 1010
(b)* 1111
(c) 1100
(d) 0101
=> Gray(n) = n XOR (n >> 1). For 10 = 1010: 1010 XOR 0101 = 1111.
!py assert ans == format(gray(10), "04b")

?2 [Codes] The largest decimal number 9999 is stored in BCD (4 bits per digit). The number of bits needed is
(a) 14
(b)* 16
(c) 13
(d) 20
=> BCD uses 4 bits for each decimal digit, so 4 digits need 4 × 4 = 16 bits. Plain binary would need only 14 bits (2¹⁴ = 16384 > 9999).
!py assert num(ans) == 4 * len("9999") and (9999).bit_length() == 14
