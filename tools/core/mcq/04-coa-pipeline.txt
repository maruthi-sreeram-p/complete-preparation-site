# Computer Organisation Part 4, performance and pipelining: original questions. Format: see tools/build_gate.py

?2 [CPU time] A program executes 4 × 10⁹ instructions with an average CPI of 2 on a 4 GHz processor. Its execution time is
(a) 0.5 s
(b) 1 s
(c)* 2 s
(d) 8 s
=> Time = IC × CPI / f = (4 × 10⁹ × 2) / (4 × 10⁹ Hz) = 2 seconds.
!py assert num(ans) == 4e9 * 2 / 4e9

?2 [CPI] A processor's instruction mix is 50% ALU instructions with CPI 1, 30% loads and stores with CPI 2, and 20% branches with CPI 4. The average CPI is
(a) 1.5
(b)* 1.9
(c) 2.3
(d) 2.33
=> CPI = 0.5 × 1 + 0.3 × 2 + 0.2 × 4 = 0.5 + 0.6 + 0.8 = 1.9. The unweighted mean (1 + 2 + 4)/3 ≈ 2.33 ignores how often each class occurs.
!py assert abs(0.5 * 1 + 0.3 * 2 + 0.2 * 4 - num(ans)) < 1e-9

?2 [MIPS] A 3 GHz processor has an average CPI of 1.5. Its native MIPS rating is
(a) 450
(b) 1,000
(c)* 2,000
(d) 4,500
=> MIPS = clock rate / (CPI × 10⁶) = 3 × 10⁹ / (1.5 × 10⁶) = 2,000.
!py assert num(ans) == 3e9 / (1.5 * 1e6)

?2 [Amdahl's law] 80% of a program's execution time is made 4 times faster, and the rest is unchanged. The overall speedup is
(a) 3.2
(b)* 2.5
(c) 4
(d) 1.8
=> Speedup = 1 / ((1 − 0.8) + 0.8/4) = 1 / (0.2 + 0.2) = 2.5. Even an infinite speedup of that part would give at most 1 / 0.2 = 5.
!py assert abs(amdahl(0.8, 4) - num(ans)) < 1e-9

?2 [Amdahl's law] 90% of a program can run in parallel. The maximum possible speedup on any number of processors is
(a) 9
(b)* 10
(c) 90
(d) unbounded
=> As the number of processors grows, the parallel part's time vanishes and only the serial 10% remains, so the speedup tends to 1 / 0.1 = 10.
!py assert num(ans) == round(1 / (1 - 0.9))

?2 [Pipeline timing] An ideal 5-stage pipeline executes 200 instructions with no stalls. The number of clock cycles needed is
(a) 200
(b) 205
(c)* 204
(d) 1,000
=> The first instruction needs 5 cycles to complete, and then one instruction completes each cycle: 5 + 200 − 1 = 204.
!py assert num(ans) == pipeline_cycles(5, 200)

?2 [Pipeline timing] An unpipelined processor takes 10 ns per instruction. It is split into a 5-stage pipeline with balanced stages of 2 ns plus 0.4 ns of pipeline-register delay per stage. For a long program the speedup from pipelining is closest to
(a) 5.0
(b)* 4.2
(c) 3.5
(d) 2.4
=> The pipelined clock period is 2 + 0.4 = 2.4 ns, and one instruction completes per period in the steady state, so the speedup is 10 / 2.4 ≈ 4.17.
!py assert abs(10 / 2.4 - num(ans)) < 0.1

?2 [Pipeline timing] The stage delays of a 5-stage pipeline are 200, 150, 250, 200 and 100 ps. Ignoring pipeline-register overhead, the clock period of the pipelined design and the ideal steady-state speedup over a non-pipelined design (whose instruction time is the sum of the stages) are
(a) 250 ps and 5
(b) 200 ps and 4.5
(c)* 250 ps and 3.6
(d) 900 ps and 1
=> The clock follows the slowest stage, 250 ps. The non-pipelined time is 200 + 150 + 250 + 200 + 100 = 900 ps, so the speedup is 900 / 250 = 3.6, less than the 5 stages because the stages are unbalanced.
!py stages = [200, 150, 250, 200, 100]
!py assert max(stages) == 250 and sum(stages) / max(stages) == 3.6

?1 [Hazards] A hazard that arises because two instructions need the same hardware unit in the same clock cycle is called a
(a) data hazard
(b) control hazard
(c)* structural hazard
(d) memory hazard
=> That is the definition of a structural hazard, for example a single memory port serving both instruction fetch and a load. Separate instruction and data caches remove it.

?2 [Hazards] Consider the sequence: ADD R1,R2,R3 followed by SUB R4,R1,R5. The dependence between them is
(a)* RAW, a true data dependence
(b) WAR, an anti-dependence
(c) WAW, an output dependence
(d) a structural hazard
=> SUB reads R1, which ADD writes, so SUB must read after ADD writes: read after write (RAW). It is the only kind of data hazard that occurs in a simple in-order pipeline.
!py assert data_hazards([("R1", "R2", "R3"), ("R4", "R1", "R5")]) == [(0, 1)]

?2 [Hazards] In a 5-stage pipeline with full forwarding, the instruction pair LW R1, 0(R2) immediately followed by ADD R3, R1, R4 causes
(a) no stall
(b)* one stall cycle
(c) two stall cycles
(d) three stall cycles
=> The loaded value is available only at the end of the MEM stage, too late to forward into the ADD's EX stage in the next cycle, so one bubble is required even with forwarding. ALU-to-ALU dependences need none.
!py assert ans.startswith("one")

?2 [Branches] 20% of the instructions are branches, 10% of the branches are mispredicted, and each misprediction costs 3 cycles. The pipeline otherwise has a CPI of 1. The effective CPI is
(a) 1.03
(b)* 1.06
(c) 1.6
(d) 1.2
=> CPI = 1 + 0.2 × 0.1 × 3 = 1.06.
!py assert abs(1 + 0.2 * 0.1 * 3 - num(ans)) < 1e-9

?1 [Branches] A loop's closing branch is taken 9 times and then not taken once, and the loop is run repeatedly. Compared with a 1-bit predictor, a 2-bit saturating counter predictor on this branch
(a) mispredicts more often
(b) mispredicts exactly as often
(c)* mispredicts about half as often: once per loop run instead of twice
(d) never mispredicts
=> A 1-bit predictor is wrong at the loop exit and again on the first iteration of the next run, 2 per run. A 2-bit counter stays in a "taken" state after the single not-taken exit, so only the exit is mispredicted: 1 per run.

?1 [Parallelism] Which of Flynn's categories describes a GPU executing the same instruction on many data elements at once?
(a) SISD
(b)* SIMD
(c) MISD
(d) MIMD
=> Single instruction, multiple data: one instruction stream operates on many data streams in lockstep. Multicore CPUs running different threads are MIMD.

?2 [Parallelism] 90% of a program is parallelisable. By Amdahl's law, the speedup on 10 processors is closest to
(a) 9.0
(b)* 5.3
(c) 10
(d) 1.9
=> Speedup = 1 / (0.1 + 0.9/10) = 1 / 0.19 ≈ 5.26. The serial 10% limits the gain well below 10.
!py assert abs(amdahl(0.9, 10) - num(ans)) < 0.1
